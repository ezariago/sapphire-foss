# Bounded Mac-to-phone files over Bluetooth

The public link now implements one ordinary local file at a time, up to **5 MiB**,
over its existing authenticated encrypted BLE session. Phone settings advertises
`fileTransferVersion: 1` and `fileTransferMaxBytes`. Android's Receive files from
paired Mac preference is disabled by default. This is not Wi-Fi bulk transfer,
phone storage browsing, reverse transfer, a remote filesystem or file clipboard.

Choose file to send in Mac Phone settings. The Continuity single-file send bridge
also routes to this implementation only for the active connected peer. Multiple
selections are rejected explicitly rather than silently dropping files. Final
symlinks, folders/special files, invalid names and oversized files are refused.
The source is read through a regular-file descriptor with bounded serial
preparation and metadata-change checks. A blocked filesystem read can outlast
cancellation; its late result cannot send an offer. The source file is unchanged.

The phone stages completed files in private app cache. In Companion → Features →
Files from Mac, Save opens Android's document picker; the user chooses the target.
No broad storage permission is required. The staged copy remains until an
explicit confirmed Discard, even after Save or Bluetooth disconnect. Another
file is refused while a completed staged file waits. Android can evict cache, so
save promptly; unavailable cache entries have an explicit discard/recovery path.
Nothing launches or opens received file content automatically.

## Protocol and boundaries

All messages require the existing encrypted session; there is no new network
listener or unprotected HTTP endpoint.

| Type | Payload / behavior |
| --- | --- |
| `file.offer` | UUID `requestId`, validated UTF-8 `name`, integer `size`, lowercase SHA-256. Android opt-in/quota/active transfer/cache checks precede staging. |
| `file.chunk` | Same ID, exact sequential integer `index`, canonical base64 `data`. Each chunk is at most 2,048 bytes; the final chunk has the exact remaining size. |
| `file.finish` | Same ID; requires exact size and matching SHA-256, syncs data/metadata and publishes the staging directory together. |
| `file.cancel` | Cancels only that active partial transfer. A previously completed file is preserved. |
| `file.transfer.result` | Matching ID, fixed state, exact next index and received byte count. Mac validates counters/state before sending one more chunk. Ready is offer acceptance; Complete is verified private-cache staging, not Save to Downloads. |

The sender keeps one chunk awaiting acknowledgement, has a 45-second phase
deadline and a 10-minute total budget. Android uses a 60-second idle and 10-minute
total budget, bounded worker queues and one active/one completed staging slot.
Peer/session changes, disabling and cancellation retire pending work. A completed
file can win a cancellation/disconnect race; status does not promise it vanished.
Only this feature's incomplete/discarded staging directories are cleaned up.
Recent IDs are bounded in memory, not a durable cross-restart delivery ledger.

Remote names never become local paths. Cache file/directory names are generated;
publication never replaces an existing completed staging directory. Save validates
size and hash while copying and reports success only after stream close. Failed
saves retain the staged copy when available; a chosen document may be partial.
Sapphire does not delete that user-selected destination after a failure. This is
not a read-back verification of the document provider's eventual storage.

## Verification and remaining work

- `test-phone-file-transfer.sh`: actual bounded file descriptor reads, ordinary
  file/symlink/directory/FIFO/oversize refusal, names, chunk reconstruction,
  exact/fractional/stale/out-of-order acknowledgements, empty files and plaintext
  rejection. All input files are UUID-owned synthetic fixtures.
- Android JVM receiver tests: real isolated staging, malformed sizes/names/chunks,
  missing/corrupt data, digest mismatch, disabled/expired/cancelled flows, completed
  file preservation, restart, explicit discard and simulated cache eviction.
  Verified-copy fixtures cover incorrect sizes/hashes and failing output streams.
- The separate permission-free USB fixture consumes packets generated by the Mac
  policy (`devicechecks/src/main/assets/mac-file-transfer.json`). On the Samsung,
  the production Android receiver reconstructed 4,097 exact synthetic bytes,
  verified/published/copied them, preserved them across simulated disconnect, then
  explicitly discarded its own fixture copy. Crypto/framing checks also passed.
  No external activity or normal companion data was used. The fixture was removed
  and the phone returned to Dozing.
- Full Mac app build/signature checks and Android app/helper builds and debug lint
  check integration. The normal companion was not installed by the isolated test.

### Live encrypted BLE staging check (24 October)

The Samsung was updated in place from companion 0.3.0 to the built 0.5.0 debug APK
with a matching signing certificate. Saved pairing was retained and the Mac
reconnected securely without pairing approval or clearing app data. Both sides
ran the production encrypted BLE, framing, acknowledgement, sender and receiver
paths. An explicitly enabled Mac local diagnostic command can generate only the
fixed `sapphire-file-transfer-fixture.bin` payload (4,097 bytes, byte i = i % 251);
it cannot select an arbitrary source path. The debug-only phone fixture binds
verification/discard to the exact transfer UUID, fixed name, size and digest.

`test-phone-file-transfer-live.py` passed disabled-receive rejection, successful
staging, an independent phone read and exact-byte/SHA-256 comparison, and discard
of that owned transfer. It restored the original Files preference. No document
picker, user file, browser, SMS composer or call was used. The normal companion
was updated for this check, unlike the earlier isolated fixture. The Mac then
exited diagnostic mode, its temporary files were removed, normal Sapphire startup
was restored, and the phone was verified Dozing with USB stay-awake off. Evidence:
`build/phone-file-live-device.log`.

The harness refuses existing active/staged files and restores only its own
preference snapshot. A fake-transport test covers blocked setup, verification
failure, restoration failure and a wake during staging, always attempting sleep
and preserving exact UUID case. No real ADB is used by that test. It runs in macOS CI. Debug fixture
activity exclusion from the release manifest was checked; debug APKs retain
development fixtures. The Mac and Android full builds/lint, 24 Android JVM cases,
all 29 configured Mac shell scripts and separate fake-harness tests passed.
Headless diagnostic startup will not open Settings or begin/approve pairing.

File Shelf feedback, actual document-picker/provider saving, real maximum-size
throughput, cache/storage pressure and locked-phone/OEM behavior remain native
checks. No user file was transferred or modified for
tests. Wi-Fi/high-throughput bulk transfer, multiple files, phone-to-Mac transfer,
phone browsing and image/file clipboard delivery remain on the roadmap.


A later optional `--sleep-during-transfer` probe observed a wake event and rejected
its background-transfer claim. Its owned staging was discarded and preference
restoration/final sleep verification completed. This does not establish why the
phone woke; asleep/locked/OEM behaviour remains unverified. The harness checks
sleep state and the last-wake timestamp rather than treating staging success as
proof that the display stayed asleep. No persistent wake/notification setting was
changed to make the probe pass. Evidence: `build/phone-file-background-device.log`.
